# Фича (на обсуждение): интеграция gallery-dl

> Статус: **предложение / RFC**. Ничего не реализовано — документ лежит в
> `main` как часть плана, а не как описание существующего кода.
> Написан по итогам ветки `improvements`; упомянутые ниже коммиты
> (`25d09e1`, `537315e`, `b73ee49`, `049ea12`) сейчас уже в `main`.
> Решение делать/не делать — за ревью или тикетом.

## 1. Проблема и мотивация

VAdlp сейчас умеет скачивать только через yt-dlp: видео (YouTube и сотни
видеосайтов), плейлисты, субтитры, аудио. Для «максимально широкой загрузки
медиа» есть заметный пробел: **изображения и галереи** (Pixiv, DeviantArt,
Twitter/X, Reddit, e621, danbooru и т.п.), где yt-dlp слаб или не работает.

gallery-dl — зрелый CLI-инструмент (Python) именно для этой ниши:
галереи, посты, теги, фильтры, загрузка в zip, login через cookies.

Цель фичи: дать пользователю выбирать инструмент (yt-dlp / gallery-dl)
и скачивать оба класса контента из одного UI.

## 2. Goals / Non-goals

**Goals**
- Установка/обновление gallery-dl через существующий фреймворк зависимостей
  (с проверкой целостности, как yt-dlp/ffmpeg/deno).
- Возможность запустить задачу через gallery-dl: URL, папка, cookies,
  базовые опции (качество, фильтры, zip).
- Показ прогресса и логов в существующей панели активности.
- Очередь, журнал, уведомления, сессии работают для обоих инструментов.

**Non-goals (пока)**
- Полная эмуляция всех возможностей gallery-dl в UI (конфиг-файлы,
  per-site опции, скрипты фильтрации) — слишком большая поверхность.
- Рефакторинг под абстракцию «произвольных бэкендов» (см. Вариант C).

## 3. Варианты реализации

### Вариант A — Минимальный («tool switch»)
**Что:** gallery-dl как опциональная зависимость + переключатель
инструмента в Download-табе. Пробрасываются только базовые поля:
URL, папка вывода, cookies, логин/пароль, аргументы.

- Задача в очереди помечается инструментом (`tool: "ytdlp" | "gallerydl"`).
- Новый runner в `internal/downloader` с парсером прогресса gallery-dl
  (см. п. 5.2) или переключение внутри существующего runner.
- UI: переключатель в Download-табе; очередь показывает значок инструмента.

**Плюсы:** малый объём; сразу покрывает 90% пользы.
**Минусы:** не всё настраивается из UI; gallery-dl.conf по-прежнему ручной.

### Вариант B — Полноценный таб («gallery»)
Всё из A + отдельный таб настроек gallery-dl:
- управление `gallery-dl.conf` (сохранение/загрузка из приложения),
- фильтры (`--filter`), диапазоны, `--zip`, `--write-metadata`,
  выбор сайтов/пресетов,
- `-g` probe (предпросмотр найденного контента в FormatPickerModal-стиле).

**Плюсы:** максимальная ценность для целевой аудитории (pixiv/deviantart).
**Минусы:** самый большой объём из осмысленных вариантов; длинная поддержка
(опции gallery-dl меняются).

### Вариант C — Абстракция «бэкенды» (НЕ рекомендуется сейчас)
Интерфейс `Backend { Probe, Run, Cancel }`, плагины через общий контракт,
конфиг-модель на каждый инструмент.

**Плюсы:** третьи инструменты (aria2, yt-dlp-подобные форки) подключаются
тривиально.
**Минусы:** большой рефакторинг ради пока одной фичи; риск сломать
отлаженный pipeline (прогресс, очереди, отмена по taskID из `b73ee49`).
**Когда стоит:** если появится 3-й инструмент с реальным спросом — тогда
рефакторинг окупится.

### Вариант D — Внешний/гибридный (самый дешёвый пилот)
Не интегрировать, а сделать «Custom tool»-режим: пользователь сам указывает
путь к любому бинарнику (gallery-dl и т.п.), а приложение пробрасывает
URL/папку/`extraArgs` и показывает stdout как логи.
- По сути это небольшое расширение уже существующего `extraArgs`.
- Прогресс-бар не гарантирован (парсер чужого вывода), но логи видны.

**Плюсы:** дни, а не недели; проверка гипотезы спроса до инвестиций.
**Минусы:** не настоящая интеграция; UX ниже.

## 4. Технические вызовы

### 4.1. Нет официального standalone-бинарника
gallery-dl — Python-пакет, официально распространяется через PyPI.
Варианты доставки:
1. **PyPI + системный Python** — требует наличия python на машине
   (проверка `python -V`, установка `pip install gallery-dl`).
2. **Bundled Python** — таскать Python-рантайм (~30+ МБ) или использовать
   `python -m zipapp`-сборки; сложнее честная проверка целостности.
3. **Неофициальные exe-сборки** (WinPython/portable-сообщества) — риск
   безопасности, несовместим с политикой «только проверенные чексуммы»
   из `25d09e1`.
4. **Автосборка .exe (PyInstaller) в CI проекта** — надёжно, но требует
   инфраструктуру сборки и публикации артефактов.

Текущая модель updater'а (один .exe + SHA-256 манифест) ломается:
`updater` умеет манифесты (`SHA2-256SUMS` и т.п.) — для PyPI придётся
забирать хэши из API PyPI (`https://pypi.org/pypi/gallery-dl/json`) —
новый код в `checksum.go`, либо фикс-версии и проверка по sha256 из JSON.

### 4.2. Другой формат вывода/прогресса
- yt-dlp: `[download] 42.1% of ...` — под это заточены `progressRegex`,
  `IsProgressLine`, `speedRegex` (см. `537315e`).
- gallery-dl: свои строки прогресса (`[download][...]`, ETA в другом виде)
  и verbose-режим. Нужен отдельный парсер (см. 5.2), нельзя просто
  переиспользовать существующий фильтр логов.
- Probe: `yt-dlp -j` не работает. gallery-dl даёт `-g/--get-urls`
  (список URL) — можно строить упрощённый предпросмотр (количество/размер).

### 4.3. Конфигурация
- `ConfigDTO` заточен под yt-dlp (форматы, субтитры, контейнеры и т.д. —
  большая часть бессмысленна для gallery-dl).
- gallery-dl реально настраивается через `gallery-dl.conf` (YAML-подобный
  формат). CLI-флагов для всего нет.
- Предложение: хранить `tool` в `QueueTaskDTO`/`ConfigDTO`
  (`tool: "ytdlp" | "gallerydl"`), а для gallery-dl использовать
  подмножество полей + путь к conf-файлу + raw `extraArgs`.

### 4.4. Инфраструктура, которая переиспользуется без изменений
- Очередь, пауза/возобновление, отмена по taskID, журнал, уведомления,
  профили, сессии, i18n, «прогресс по задачам» (`taskProgress`).
- `DependenciesTab`: новый dep `gallerydl` со своим install/update/guard —
  нужно только решить вопрос доставки (4.1).

## 5. Проектирование (черновик для обсуждения)

### 5.1. Данные
```go
// internal/downloader
type Tool string
const (
    ToolYtDlp    Tool = "ytdlp"
    ToolGalleryDl Tool = "gallerydl"
)
```
- `ConfigDTO.Tool` (или отдельное поле в `QueueTaskDTO`); `defaultConfig`
  возвращает `ytdlp` — обратная совместимость.
- Прогресс-события уже содержат `taskId` — менять не нужно.

### 5.2. Runner
- `internal/downloader/runner.go` → фабрика команд по `Tool`.
- Парсер прогресса gallery-dl: отдельный regex-набор
  (`[download] ... / ...`?), экспортированный предикат
  `IsGalleryDlProgressLine` (по аналогии с `IsProgressLine`).
- Логи: общий фильтр `IsLogLine(line)` для обоих инструментов.

### 5.3. Updater
- `internal/updater/gallerydl.go`: источник версии — PyPI JSON
  (`https://pypi.org/pypi/gallery-dl/json`), скачивание wheel,
  извлечение в tools-каталог + проверка sha256 из PyPI API.
- ВАЖНО: сохранить политику «не можем проверить → не устанавливаем»
  из `25d09e1`.

### 5.4. UI
- Вариант A: сегментированный переключатель в Download-табе
  (`yt-dlp | gallery-dl`); нерелевантные поля скрываются/дизейблятся.
- Вариант B: таб `gallery` в `components/tabs/` (по образцу существующих
  табов после `049ea12`), сохранение/загрузка `gallery-dl.conf`
  через существующие `PickFile`/`PickSaveFile`.

## 6. Открытые вопросы (для обсуждения)
1. Какой вариант: A, B, C, D? Кто-нибудь реально будет качать Pixiv/DA?
2. Доставка: системный Python, bundled runtime, PyInstaller-CI, или
   просто pip-установка с документированием требования?
3. Нужна ли проверка чексумм через PyPI API или достаточно фиксации
   версии + хэша в репозитории приложения?
4. Cookie-профили: переиспользовать `useCookiesBrowser` (у gallery-dl
   есть свой `--cookies-from-browser`) или ввести отдельные поля?
5. Файл конфигурации: полный YAML-редактор в UI или только путь к
   существующему conf + raw-аргументы?
6. Политика ToS/риски сайтов: нужны ли встроенные дисклеймеры
   (личное использование) при выборе gallery-dl?
7. Объединять ли загрузки с yt-dlp в одну очередь (tool у каждой задачи)
   или делать отдельную вкладку-очередь?

## 7. Оценка трудозатрат (грубо, на основе текущей кодовой базы)
| Вариант | Коммитов | Объём | Риск |
|---|---|---|---|
| D (custom tool пилот) | 1–2 | маленький | низкий |
| A (tool switch) | 4–6 | средний | средний (parser) |
| B (полный таб) | 8–12 | большой | высокий (conf-совместимость) |
| C (абстракция бэкендов) | 10–15 | очень большой | высокий (регрессии) |

## 8. Критерии приёмки (когда решим делать)
- `go test ./...`, `npm run build`, `npm test` — зелёные.
- Установка gallery-dl из приложения проходит проверку целостности.
- Скачивание тестовой галереи (например, публичной страницы) показывает
  прогресс в панели активности, задача помечается инструментом.
- Отмена задачи останавливает только её (регрессия `b73ee49` исключена
  тестом).
